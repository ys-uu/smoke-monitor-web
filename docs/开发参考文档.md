## 2. 项目概述

### 2.1 系统目标

对监控视频流进行**实时抽烟行为检测**，在画面上标注人脸与香烟、对违规人员给出报警，并把违规事件（含现场快照、置信度、来源、时间）落库，提供事件查询、人工复核标注与 CSV 导出。

### 2.2 核心检测方案：两阶段推理

系统采用**第一阶段引导的两阶段检测**（这是当前主方案，也是唯一已实现的在线推理路径）：

1. **第一阶段 · 人物头部检测与跟踪**：定位画面中的人并分配跟踪 ID，再在检测框基础上外扩得到"搜索区域 ROI"。第一阶段在「模型选择」区域按具体权重文件选择，所选文件位于 `stage1/face` 还是 `stage1/head` 子目录决定使用哪种检测器：
   - `face`（默认）：YOLO 人脸检测，只在能看到五官时检出，**侧脸、背面（后脑勺）会漏检**；
   - `head`：YOLO 单类头部检测，标注整个头部（含后脑勺），**侧脸、背面都能定位**，用于弥补人脸漏检。两种检测器都用 BoT-SORT 跟踪器分配稳定 ID；
2. **第二阶段 · ROI 内香烟检测**：只在每个 ROI 裁剪区域内运行香烟检测模型（同样在「模型选择」区域按 `stage2` 目录内的权重选择），把检测框映射回整帧坐标，再对跨区域的重叠结果做全局去重。

相比"对整帧直接检测香烟"的单阶段方案，两阶段把搜索范围限定在人物头部周边，**显著降低把手机等深色物体误判为香烟的误报**，代价是单帧计算量更大、且依赖第一阶段能先找到人。

> 背面（看不到脸）时第二阶段在 ROI 内通常检不到香烟，自然不会报警，逻辑上不会因此误报，只是该 ROI 会空跑一次香烟推理。

### 2.3 视频源类型

系统支持四类输入，统一抽象为视频源：

| source_type | 含义 | 标识示例 |
| --- | --- | --- |
| `sample` | 工程内置样例视频 | `sample:samples/smoke_test2.mp4` |
| `local` | 本机绝对路径直读（受白名单约束） | `local:<hash>` |
| `upload` | 浏览器上传的视频文件 | `upload:<id>` |
| `camera` | 本机摄像头实时流 | `camera:0` |

## 3. 技术选型与总体架构

### 3.1 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 后端 | Flask 3.x（应用工厂 + 蓝图） | 轻量、无重型框架，团队上手成本低 |
| 前端 | 原生 HTML / CSS / JavaScript | **无构建链、无 npm 依赖**，静态文件直接由 Flask 托管 |
| 推理 | Ultralytics YOLO（PyTorch）、OpenCV、BoT-SORT | 人脸与香烟两个模型，GPU 优先、CPU 可回退 |
| 数据库 | MySQL 8.0（Docker 容器） | 独立容器，不与其他服务混用；应急可切 SQLite |
| 实时画面 | MJPEG 流（`multipart/x-mixed-replace`） | 浏览器原生可播，无需 WebSocket |

选型原则：**能用简单方案就不引入复杂依赖**；前后端不设打包构建步骤，克隆仓库、装好依赖、起好数据库即可运行。

### 3.2 分层与数据流

```
浏览器 (templates + static)
        │  HTTP / JSON            ▲  MJPEG 视频流
        ▼                         │
Flask 蓝图 (pages / sources / session_stream / events)
        │
        ├─ SessionManager（会话生命周期 + 后台读帧线程）
        │        ├─ SourceResolver（视频源解析/上传/探测）
        │        ├─ InferEngine（两阶段：FaceDetector → 香烟检测 → 投票 → 绘制 → JPEG）
        │        └─ EventRecorder（报警冷却/心跳/快照 → 落库）
        │
        └─ SQLAlchemy ORM (DetectionEvent) → MySQL
```

一帧的处理链路：后台线程从视频源读帧 → 推理引擎产出标注 JPEG 与 info → 一方面通过 MJPEG 推给浏览器，另一方面由事件记录器判断是否需要落库。

## 4. 本地开发环境搭建

### 4.1 前置要求

- Python 3.10（推荐，与推理依赖验证版本一致）；
- 可用的 Python 虚拟环境（conda / venv 均可）；
- Docker Desktop（用于启动 MySQL；若用应急 SQLite 可暂不需要）；
- 有 NVIDIA 显卡时安装匹配的 CUDA 版 PyTorch；无显卡也能用 CPU 跑，仅帧率较低。

### 4.2 安装步骤

```bash
# 1. 克隆仓库
git clone https://github.com/ys-uu/smoke-monitor-web.git
cd smoke-monitor-web

# 2. 在虚拟环境中安装依赖
pip install -r requirements.txt

# 3. 准备环境变量（数据库账号、端口等）
copy deploy\mysql\.env.example deploy\mysql\.env      # Windows
# cp deploy/mysql/.env.example deploy/mysql/.env      # macOS/Linux

# 4. 启动 MySQL 容器
docker compose up -d

# 5. 启动 Web 服务
python run_web.py
```

启动后浏览器访问 `http://127.0.0.1:8010`。

### 4.3 验证环境

- 打开 `GET /api/health`：返回 `db_ok`、引擎与配置状态；数据库未就绪时这里会给出中文可排查错误，且不阻止 Web 进程启动；
- 打开 `GET /api/engine/selftest`：引擎自检，确认权重可加载、推理可跑通。

## 5. 代码规范与工程约定

### 5.1 通用约定

- **配置集中**：所有可调参数集中在 `webapp/config.py`，模块不散落魔法数字；
- **统一响应**：后端接口统一用 `api_ok / api_error` 返回，业务错误抛 `ApiError`，不直接返回裸字典或随意状态码；
- **绘制与 IO 分离**：推理引擎只负责计算和在画面上绘制，不做文件、数据库操作；落库、快照由 `EventRecorder` 负责；
- **不污染调用方**：`process_frame` 内部复制帧再绘制，不修改调用方持有的原始帧；
- **路径自包含**：文件优先放在工程内（`models/`、`samples/`、`data/`），数据库只存相对路径。

### 5.2 Python 风格

- 模块顶部用注释说明职责；关键步骤写**逐行中文注释**，命名语义化；
- 类型注解尽量齐全（`from __future__ import annotations`）；
- 数据结构优先用 `dataclass`（如 `InferParams`、`FaceRegion`、`VoteState`）；
- 常量统一大写、顶部集中声明；
- 拒绝过度封装与冗余目录，扁平清晰优先。

### 5.3 前端风格

- 原生 JS，不引入框架与构建工具；按页面拆文件（监控、事件、API 封装、入口）；
- 接口调用统一走 `static/js/api.js`，不在各页面散落 fetch；
- 画面文字：OpenCV 绘制的 HUD 不支持中文，**画面内文字统一英文**；页面 DOM 文案用中文。

### 5.4 脚本与临时文件

- 可复用工具放进统一位置，临时脚本用完即删，不在根目录堆积；
- `data/`、`runs/` 为运行产物，不提交个人临时数据。

## 7. 两阶段在线推理引擎（核心）

本章对应 `webapp/services/infer_engine.py` 与 `face_detector.py`，是后端与模型成员最需要对齐的部分。

### 7.1 关键类与职责

| 类 / 函数 | 文件 | 职责 |
| --- | --- | --- |
| `InferParams` | infer_engine.py | 一次会话的全部推理参数（dataclass，含 `validate`） |
| `VoteState` | infer_engine.py | 跟踪器、投票历史、报警保持（hold）、帧计数与 FPS 平滑状态 |
| `new_vote_state` | infer_engine.py | 为每个会话/视频源新建一份独立状态 |
| `InferEngine` | infer_engine.py | 按 `detector_kind`（由所选 stage1 子目录推断）构建第一阶段检测器，逐帧执行两阶段推理 |
| `FaceDetector` | face_detector.py | 人脸检测、调用 BoT-SORT、生成 ROI |
| `HeadDetector` | head_detector.py | 头部检测（含侧脸/背面）、复用 BoT-SORT、生成 ROI，接口与 FaceDetector 一致 |
| `FaceRegion` | face_detector.py | 单个区域的原始框 `box`、外扩 ROI `crop`、跟踪 ID（head 也复用此结构） |
| `new_face_tracker` | face_detector.py | 创建 BoT-SORT 跟踪器（face/head 共用） |
| `face_region` | face_detector.py | 人脸框按固定像素外扩并裁剪到画面边界 |
| `head_region` | head_detector.py | 头部框按固定像素外扩并裁剪到画面边界 |
| `list_stage1_models` / `list_stage2_models` | model_catalog.py | 扫描分阶段目录，返回前端下拉可选项（一阶段带 kind 分组） |
| `resolve_stage1` / `resolve_stage2` | model_catalog.py | 白名单 + 目录内安全解析，返回 kind 与权重绝对路径，拦截路径穿越 |
| `load_yolo` | model_loader.py | 加载权重，兼容旧人脸权重 |

### 7.2 单帧处理流程（`InferEngine.process_frame`）

```
输入 BGR 帧 frame + 跨帧状态 state
  │
  ① 第一阶段检测与跟踪  detector.detect(frame, tracker, expand_pad)
  │     · 选中 stage1/face 模型：FaceDetector，人脸推理（imgsz=640, conf=face_conf）
  │     · 选中 stage1/head 模型：HeadDetector，头部推理（imgsz=640, conf=head_conf）
  │     · 两者都按固定像素 expand_pad 外扩，用 BoT-SORT 更新，分配/延续 track_id，ROI 不越画面边界
  │     · 无区域 → 返回空列表，后续不做香烟检测（该帧零检出）
  │
  ② ROI 内香烟检测  _detect_cigarettes(frame, regions)
  │     · 对每个 ROI 裁剪 crop，香烟模型在 crop 内推理（imgsz=960, conf, iou）
  │     · 把 crop 内坐标映射回整帧坐标
  │     · 相邻区域 ROI 可能重叠、重复检出同一支烟
  │       → cv2.dnn.NMSBoxes 全局去重（GLOBAL_NMS_IOU=0.40）
  │
  ③ 归属判断  _cigarette_in_region
  │     · 按烟框中心点是否落在该区域 ROI 内，判定每个 track_id 是否"有烟"
  │
  ④ 投票/报警保持  state.update(observations)
  │     · use_vote=False：直接采用当前帧，有烟即报警（单帧口径）
  │     · use_vote=True：按 track_id 各自维护窗口队列，累计达阈值才报警
  │     · 报警滞回（hold）：报警后 hold_frames 帧内即使漏检仍判报警，红框跟随当前头部框，避免闪烁
  │
  ⑤ 绘制  _draw_detections + _draw_hud
  │     · 灰色 ROI、橙色烟框、人脸框（绿 normal / 红 alarm）
  │     · 人脸标签 ID + normal/SMOKE（启用投票时附 x/window）
  │     · 顶部 HUD、报警时 SMOKING ALARM 角标
  │
  ⑥ JPEG 编码（quality=85）
  │
输出 (jpeg_bytes, info)
```

### 7.3 投票机制（当前实现口径）

投票由 `VoteState.update` 实现，**按跟踪 ID 独立累计，不做整帧统一投票**：

- 每个 `track_id` 维护一个 `deque(maxlen=vote_window)`，逐帧追加该人"当前是否有烟（0/1）"；
- 窗口内票数之和 `count ≥ vote_threshold` 时，该人判为报警；
- 某 `track_id` 从画面消失，其历史队列立即删除，**票数不会跨人、不会串到新 ID**；
- 跟踪 ID 暂缺（跟踪器未分配）时按当前帧结果处理，不做跨帧累计。

**默认 `use_vote=False`、窗口 1、阈值 1**，即默认不做时间维度投票，单帧检出即报警。前端可在开始会话前开启投票并设置窗口/阈值。

**报警红框保持（hold，独立于投票）**：解决香烟检测帧间抖动导致红框闪烁。`VoteState` 另用 `alarm_hold` 记录每个 `track_id` 最近一次报警帧号——当前帧报警则刷新；当前帧漏检但与最近报警帧间隔不超过 `alarm_hold_frames` 时仍判报警，红框用**当前帧实时头部框**跟随（人物移动不错位）；超过保持帧数才恢复绿色。默认 12 帧、前端可调，设 0 关闭。保持期内若没有香烟框，`EventRecorder` 不落库，因此该机制只影响显示、不制造空洞记录。

> 历史讨论中曾提出"整帧统一投票、窗口 4 阈值 2"，与当前"按 ID 投票且默认关闭"的实现不一致，见第 14 章待决策项。

### 7.4 输出 info 字段

`process_frame` 返回的 `info` 字典字段（也是前端状态展示与落库的依据）：

| 字段 | 含义 |
| --- | --- |
| `frame_index` | 帧序号（会话内从 1 递增） |
| `face_count` | 本帧人脸数 |
| `cig_count` | 去重后香烟框数 |
| `alarm_persons` | 判为报警的人数 |
| `max_conf` | 本帧最高香烟置信度 |
| `infer_ms` | 本帧推理耗时（毫秒） |
| `fps_ema` | 指数平滑帧率（0.9 旧值 + 0.1 当前值） |
| `device` | 实际推理设备描述 |

### 7.5 引擎加载与缓存

- `InferEngine.__init__` 加载两个模型并各做一次 dummy 预热，避免首帧明显卡顿；
- 设备解析 `_resolve_device`：`auto` 优先 CUDA，显式指定 GPU 但 CUDA 不可用时回退 CPU；
- `engine_holder.py` 提供进程内单例与按权重/参数的缓存，避免重复加载；
- CPU 路径限制 `OMP/MKL` 线程数，避免占满笔记本核心。

### 7.6 第一阶段 head 头部检测方案（新增）

**背景**：原 `FaceDetector` 只在能看到五官时检出，侧脸、背面会漏，导致这些人无法进入第二阶段。head 检测器标注整个头部（含后脑勺），各种朝向都能定位。

**数据与训练（模型训练负责人，在独立训练工程完成，不在本仓库）**：

- 数据集：CrowdHuman（15000 训练 / 4370 验证，ODGT 标注），取其中的 hbox 头部框，覆盖教室、街景等密集人群，含大量侧脸、背面、遮挡；
- 数据构建：ODGT → YOLO 单类 head（类别 id 0），跳过 ignore/mask 标注，最终 19370 图、约 42.9 万有效头部框；
- 训练：YOLOv8n 单类 head，imgsz 960、batch 32、epochs 100、seed 42，跟踪口径与在线推理一致；
- 验证指标：mAP50 ≈ 0.778、mAP50-95 ≈ 0.491（epoch 83 欠费中断时已收敛，best.pt 即最终可用权重）。

**产物接入本工程**：

- 训练产出的最优权重命名为 `head_crowdhuman_best.pt`，已放入本工程 `models/stage1/head/`；
- 在「模型选择」区域选中该文件即按 head 路径加载，第二阶段、跟踪、投票、绘制全部复用，无需改其他代码。

**切换方式**：

- 前端：「模型选择」区域的一阶段下拉选择 head 分组内的权重，开始会话前生效；
- 全局默认：设置环境变量 `SMOKE_DETECTOR_KIND=head` 仅影响引擎自检的默认 kind；
- 前端默认仍选中 `face`；head 权重已就绪，可随时下拉切换对比两种第一阶段的检测效果。
- 后续新增一阶段权重：人脸放 `stage1/face/`、头部放 `stage1/head/`；新增香烟权重放 `stage2/`，刷新页面后下拉自动出现，无需改代码。

## 8. 数据库设计

### 8.1 概况

当前仅一张事件表 `detection_event`，ORM 为 `webapp/models.py:DetectionEvent`，建表脚本 `deploy/mysql/initdb/schema.sql`，两者保持一致。列类型使用通用 Integer/Float/String/Text/DateTime，**不使用 MySQL 专有 JSON 类型**，以便应急切 SQLite 直接建表。图片以文件存磁盘，数据库只存相对路径。

### 8.2 表结构（18 列）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | Integer PK 自增 | 主键 |
| `event_time` | DateTime | 事件墙钟本地时间 |
| `source_id` | String(64) | 来源标识（sample/local/upload/camera） |
| `source_type` | String(16) | 来源类型 |
| `source_name` | String(255) | 来源展示名 |
| `frame_index` | Integer 可空 | 帧号（实时流可空） |

| `max_conf` | Float 可空 | 最高置信度 |
| `vote_sum` | Integer 可空 | 投票计数 |
| `vote_window` | Integer 可空 | 投票窗口 |
| `model_name` | String(128) | 所用香烟权重文件名 |
| `snapshot_relpath` | String(512) | 快照相对 `data/web_events` 的路径 |
| `bbox_json` | Text | 该帧烟框列表 JSON 文本 |
| `status` | String(16) | 处置状态：`open` / `confirmed` / `false_alarm` |

索引（3 个）：

- `idx_event_time`（event_time）：按时间排序/过滤；
- `idx_source_time`（source_id, event_time）：按来源查时间线；

### 8.3 落库规则

- **只有报警帧（`is_alarm` 且有烟框）才落库**，单帧检测到但不满足报警口径的不写库；
- `EventRecorder.observe` 维护冷却状态机：受冷却时间约束，`alarm_start` 首次记录、持续报警期间按 `heartbeat` 补记；
- 快照、心跳可在开始会话前开关；写库失败会回滚并重试，不静默丢事件。

### 11.1 单元测试

`tests/` 基于 unittest，共 17 个用例（两个文件）。`test_two_stage_inference.py`（11 个）覆盖两阶段关键逻辑：

10. 保持帧数为 0 时不保持、立即恢复；
11. 无跟踪 ID 不参与保持。

### 11.3 实测性能基线（参考）

> 测试环境：笔记本端独立显卡（RTX 4060 级别）、GPU 推理；样例 `smoke_test2.mp4`，共 372 帧、源 30 FPS；默认 n960 权重。数据为本地实测，不同机器会有差异，仅作量级参考。

| 配置 | 人脸帧 | 检出香烟帧 | 报警帧 | 平均推理 | 吞吐 |
| --- | --- | --- | --- | --- | --- |
| 投票关（默认，单帧即报警） | 307 / 372 | 15（4.03%） | 15 | 98.3 ms | 9.26 FPS |
| 投票开（阈值 2 / 窗口 4） | 307 / 372 | 15（4.03%） | 20 | 101.2 ms | 9.0 FPS |

说明：

- 两种配置下**实际检出香烟的帧都是 15 帧**；开启投票后报警帧为 20，是因为投票属"滞后确认"——一旦某人满足阈值，报警状态会在窗口内连续保持若干帧，形成更稳定的连续报警段，避免单帧结果来回闪烁；
- 当前 GPU 下两阶段吞吐约 9–10 FPS，低于源视频 30 FPS，实时演示建议配合样例视频或接受一定延迟，答辩可提前录屏兜底；
- 目视对照曾验证：整帧直接检测会把画面中的黑色手机误判为香烟，而两阶段在同画面正确零检出、真实抽烟时能以较高置信度检出，体现两阶段在**降低误报**上的优势。

- 应用启动时自动 `create_all` 建表；建表失败不阻止进程，健康检查会如实上报，系统**不做自动降级**（避免数据写到错误位置），需要 SQLite 时由开发者显式改连接串。

### 12.3 运行目录

- 事件快照：`data/web_events/<日期>/<uuid>.jpg`；
- 上传文件：`data/web_uploads/<日期>/...`；
- 这些目录运行时自动创建，属运行产物，不作为源码提交。

## 15. 常见问题 FAQ

**Q1：克隆后跑不起来，提示数据库连不上？**
先 `docker compose up -d` 起 MySQL，再看 `/api/health` 的中文报错；应急可把 `SMOKE_DATABASE_URL` 改为 SQLite 连接串。

**Q2：为什么没有 npm install / build 步骤？**
前端是原生 HTML/CSS/JS，无构建链，静态文件由 Flask 直接托管，装好 Python 依赖即可。

**Q3：默认是怎么判定报警的？**
默认关闭投票，单帧在某人 ROI 内检出香烟即报警；可在开始会话前开启按人投票。

**Q4：推理在 GPU 还是 CPU？**
默认 auto，有 CUDA 用 GPU、否则自动回退 CPU；可在开始前显式指定。

**Q5：改参数为什么要先停止会话？**
系统明确约定运行中参数锁定、不做热更，保证一次会话内口径一致，避免中途改阈值导致结果不可比。

**Q6：检测框会画在我原始的帧上吗？**
不会，引擎内部复制后再绘制，原始帧不被修改。

**Q7：什么时候用 head 头部检测？**
当画面里有较多侧脸、背面，原人脸检测器漏检时，在「模型选择」区域的一阶段下拉里选 head 分组的 `head_crowdhuman_best.pt`（位于 `models/stage1/head/`）。背面看不到脸时第二阶段自然检不到香烟，不会因此误报。

**Q8：怎么加入自己训练的新模型？**
一阶段人脸放 `models/stage1/face/`、头部放 `models/stage1/head/`，二阶段香烟放 `models/stage2/`，只支持 `.pt`；刷新页面后对应下拉自动出现新选项，无需改代码。后端会校验选择，目录外或带 `..` 的路径一律拒绝。
